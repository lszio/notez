#+title: 0.5.x-A1+A3 UseCase Impl 拆分 + 写操作三件套
#+date: 2026-08-09
#+STARTUP: showeverything

本 spec 承接 [[file:2026-08-02-usecase-trait-split-design.org][2026-08-02 UseCase Trait 拆分设计]] 与 [[file:2026-08-02-application-error-design.org][ApplicationError 结构化变体设计]]，把 `core::application.service.rs` 1740 行的 god-impl 拆为 9 个 use-case mod 文件，并在写操作路径上落实「address uniqueness + capability + revision check」三件套，同时把 CLI/MCP 调用面切到 `Trait::fn(&mut service, ...)`。本 spec 锁掉 roadmap §0.5.x 的最后两个待办：CLI/MCP 全部公开操作迁至新协议、生成 MCP schema、写操作统一执行三件套检查。

* 1. 背景与现状

** 1.1 上游已交付

- 0.3：=ResourceAddress= / =LinkOccurrence= / =ResolvedRelation= / =derived_id= v1。
- 0.4：=ConfigPaths= / =RuntimeConfig= / =SpaceSourcesConfig= / =select_space=。
- 0.5（前两步）：
  - 9 个 =UseCase= trait 已拆完（=[[file:2026-08-02-usecase-trait-split-design.org][spec]]），但实现仍堆在 =service.rs= 一个 =impl ApplicationFacade<S>= 块里。
  - =ApplicationError= 已升级为 8 个结构化变体（=[[file:2026-08-02-application-error-design.org][spec]]），含 =RevisionConflict { expected, actual }= 与 =UnsupportedCapability { capability: &'static str }=。
  - =CapabilityCatalog= 已实现 9 个 built-in 描述符，=register_capability= 真正写入 catalog。
  - =A2=（本轮前置，HEAD =345e4aa=）：CLI =list-capabilities= 与 MCP =list_capabilities= 共用 =facade.capabilities_json()=。

** 1.2 当前痛点

- =crates/core/src/application/service.rs= 1742 行单 =impl= 块；44 个 =pub fn= + 9 个 use-case trait impl 块 + 9 个 =*_impl= 转发器，混在一起。
- CLI =main.rs= 1391 行；MCP =server.rs= 1019 行；两者对 =service.<fn>()= 的调用分散，未通过 trait 入口，编译期无法保证「能力对应 trait 存在」。
- 写操作（=upsert_resource= / =delete_resource= / =resolve_links= / =transition_task= / =add_attachment= / =create_community= / =derive_artifact= / =export_skill= / =sync_push= 等）目前仅做能力检查的提示性日志（部分方法甚至没有），address uniqueness 完全没实现，expected revision 也未落地。
- 0.5 spec §5 写的「共享 Request/Response DTO」/「CLI/MCP 全部公开操作迁至新协议」/「MCP inspect 使用真正的 inspect 用例」/「写操作统一执行 address uniqueness、capability 与 revision 检查」均未达到。

** 1.3 范围

做：

- 把 =ApplicationFacade= 9 个 use-case 的方法体从 =service.rs= god-impl 拆到 9 个新 mod 文件 =application/use_cases_impl/<trait>.rs=。
- 写操作统一执行 address uniqueness / capability / revision check 三件套；失败返回结构化 =ApplicationError=。
- CLI =main.rs= 与 MCP =server.rs= 的所有 =service.<fn>()= 写调用面切到 =Trait::fn(&mut service, ...)= 形态（read-only 路径保持 =service.<fn>()= 不动，减少 diff）。
- =MCP= =inspect= tool 改用真正的 =InspectUseCase::inspect_rules= / =space_doctor= 用例，而非当前空 stub。

不做（推迟到后续 0.6 / 1.0 切片）：

- =ApplicationError= 新增变体（=Denied= / =Principal= / =Policy= 不在本轮）。
- =Principal × Space × Source × Action × Scope= 授权维度（spec §5.2）；本轮只接 capability descriptor 是否注册 = UnsupportedCapability 检查。
- =journal= / =expected revision= 落库（spec §0.6 =B7= 任务）。
- =notez:// scheme=（spec §5.3）。
- =Change= 投递模型与 audit trace。
- =Source= stale 标记。
- =service.rs= 之外的任何领域层调整（=Resource= / =ResourceRelation= / =ObjectId= 字段不动）。
- 性能优化、benchmark。
- crates 之外的 =packages/web= / =desktop= / =mobile= / =api= 入口实质改动。

* 2. 决策

=service.rs= 目标 ≤400 行（只保留 facade struct + 9 个 use-case trait 的 44 个 =pub fn= 转发器，每转发器 1 行 =<Self as TraitUseCase>::fn(self, ...)=）。

每个 =use_cases_impl/<trait>.rs= 文件包含：

- 一行 doc 注释说明该 trait 涵盖的方法集合。
- =use= 引入（=crate::application::ApplicationFacade= / =ProjectionStore= / 必要领域类型）。
- =impl<S: ProjectionStore> <Trait> for ApplicationFacade<S> { ... }= 块，**方法体直接是原 service.rs 里的方法体**，不再有 =*_impl= 中转。
- 文件尾部如有本 trait 专属 helper（如 =ResourceUseCase::resolve= 的解析逻辑、=ScanUseCase::scan_native= 的 walkdir 调用），可放在 =use_cases_impl/<trait>_helpers.rs= 子文件。

** 2.3 CLI / MCP 调用面切到 Trait

read-only 调用 =scan_native= / =query= / =read= / =list_recent= / =list_by_source= / =query_link_occurrences= / =query_resolved_relations= / =list_links= / =diagnose_link= / =agenda= / =para_overview= / =query_segments= / =list_communities= / =list_conflicts= / =list_jobs= / =check_artifact_freshness= / =space_doctor= / =inspect_rules= / =resolve= / =resolve_address= 也走 trait 调用面；与写操作统一处理。

改造规则：

- 在 =main.rs= / =mcp/server.rs= 顶部 =use= 行加入：=use notez_core::application::use_cases::{...}= 引入所有 9 个 trait。
- 每个写/读调用点 =service.foo(args)= → =<ApplicationFacade<_> as FooUseCase>::foo(&mut service, args)=。
- 例外（不动）：=service.new= / =service.with_space= / =service.space= / =service.store= / =service.store_mut= / =service.register_format_parser= / =service.register_source_factory= / =service.register_capability= / =service.capability_catalog= / =service.capabilities_json=（这些是构造/配置/查询辅助，不是 use-case）。

最终：=cli/src/main.rs= + =cli/src/mcp/server.rs= 中「=service.<小写>=」调用只允许是上面这 10 个非 use-case 入口。=cli/src/mcp/server.rs= 387 / 396 行的 =self.service.lock()= 调用不算（field access 不是 method call）。

** 2.4 写操作三件套

=core/src/application/write_check.rs=（新文件）提供三个公开函数，每个 use-case 写方法在写之前调用：

#+begin_src rust
/// 校验同一 ResourceAddress 不会指向两个不同 ResourceRef。
/// 当前实现：把要写的 ResourceRef 转成 ResourceAddress，若 catalog 中已有该
/// address 指向另一个 ref，报 `ApplicationError::AddressUniqueness`。
pub fn check_address_uniqueness(
    facade: &ApplicationFacade<impl ProjectionStore>,
    addr: &ResourceAddress,
    candidate: &ResourceRef,
) -> Result<(), ApplicationError>;

/// 校验 capability descriptor 已注册到 catalog，否则
/// `ApplicationError::UnsupportedCapability { capability }`。
pub fn check_capability(
    facade: &ApplicationFacade<impl ProjectionStore>,
    capability: &'static str,
) -> Result<(), ApplicationError>;

/// 校验 expected revision 与 store 中当前一致，否则
/// `ApplicationError::RevisionConflict { expected, actual }`。
/// `expected` 为空字符串表示「无条件覆盖」（CLI 写场景）。
pub fn check_revision(
    facade: &ApplicationFacade<impl ProjectionStore>,
    r_ref: &ResourceRef,
    expected: &str,
) -> Result<(), ApplicationError>;
#+end_src

新增 =ApplicationError= 变体（不在本 spec 范围，由本 spec 落地时连同 error spec 增量更新）：

#+begin_src rust
pub enum ApplicationError {
    // ... 8 个现有变体 ...
    /// 同地址指向不同 ref（address uniqueness）
    AddressUniqueness { addr: ResourceAddress, existing: ResourceRef, candidate: ResourceRef },
}
#+end_src

本 spec **不引入** =Denied= / =Principal= / =Policy= / =Audit= 变体；那批 0.6 / MVP-2 任务。

各 use-case 写方法在入口处顺序调用：

#+begin_src rust
impl<S: ProjectionStore> ResourceUseCase for ApplicationFacade<S> {
    fn upsert_resource(&mut self, resource: Resource) -> Result<(), ApplicationError> {
        write_check::check_capability(self, "resource")?;
        if !resource.revision.is_empty() {
            write_check::check_revision(self, &resource.r#ref, &resource.revision)?;
        }
        let addr = ResourceAddress::from(resource.r#ref);
        write_check::check_address_uniqueness(self, &addr, &resource.r#ref)?;
        // 原 service.rs 中 upsert_resource 的方法体
        self.store.upsert_resource(&resource)
            .map_err(|e| ApplicationError::Storage { kind: StorageErrorKind::Sqlite, message: e.to_string() })?;
        Ok(())
    }
    // ...
}
#+end_src

读方法不调用三件套；只有「会改 projection / journal / 文件」的路径才需要。

三件套失败的语义：

- =check_capability= 失败 → =UnsupportedCapability { capability } =，CLI exit code 6（已在 0.5 error spec 中映射）。
- =check_revision= 失败 → =RevisionConflict { expected, actual } =，CLI exit code 9。
- =check_address_uniqueness= 失败 → =AddressUniqueness=，本轮新增；exit code 10（追加到 =exit_code_for= 表）。

MCP 错误按 =struct_err= 已有结构透出（{ kind, message }）。

** 2.5 =Inspect= MCP tool 改用真正 inspect 用例

当前 =mcp/server.rs= 的 =inspect= tool 大半走 =link_resolution=（属于 =LinkUseCase=）。本轮把 =inspect= 拆为两个 tool：

- =inspect_rules=：接受 ={ "ref": "..." }=，调 =<AppFacade as InspectUseCase>::inspect_rules=。
- =space_doctor=：保留现有 =space_doctor= tool（已用 =InspectUseCase::space_doctor=，无需改）。

=inspect= 旧 tool 在本轮删除（无向后兼容承诺，旧 tool 仅在孤儿测试里被引用，且 0.5 spec 要求「MCP inspect 使用真正的 inspect 用例」），同时把 =doctor_mcp.rs= 孤儿测试里的期望同步迁移到 =inspect_rules_mcp.rs=（落到 =crates/cli/tests/= 下，cargo 可见）。

** 2.7 ApplicationError 新增变体的兼容处理

新增 =AddressUniqueness= 变体 =#[serde(rename_all = "snake_case")]= 形式：

#+begin_src json
{ "kind": "address_uniqueness",
  "addr": { "kind": "ref", "value": "heading:..." },
  "existing": "heading:01J...",
  "candidate": "heading:01J...",
  "message": "address uniqueness: ... already bound to ..." }
#+end_src

=cli/src/main.rs= 的 =exit_code_for= 加：

#+begin_src rust
ApplicationError::AddressUniqueness { .. } => 10,
#+end_src

=Display= 稳定格式：

#+begin_src text
address uniqueness: <addr> already bound to <existing>; cannot rebind to <candidate>
#+end_src

=serde= 派生自动覆盖；手写 impl 已存在 =serde::Serialize= / =Deserialize= 在 =service.rs=，需要补 =AddressUniqueness= 分支（与 =RevisionConflict= 风格保持一致）。

* 5. 迁移顺序

按「先拆 mod（行为不变）→ 三件套（行为扩展）→ 切调用面（结构改造）」三阶段，每阶段单 commit。

1. *阶段 1 — 拆 mod*：
   - 新增 =use_cases_impl/= 9 个 mod 文件，把 =service.rs= 现有 9 个 use-case impl 块方法体复制过去。
   - =service.rs= 删除这 9 个 impl 块；44 个 =pub fn= 转发器保留为单行 =<Self as TraitUseCase>::fn(self, ...)=。
   - 验证 =cargo test --workspace= 0 回归。=service.rs= 目标 ≤ 600 行。
   - 1 commit。
2. *阶段 2 — 写操作三件套*：
   - 新增 =core/src/application/write_check.rs= + 3 个 helper。
   - =ApplicationError= 加 =AddressUniqueness= 变体 + serde impl + Display 格式。
   - =use_cases_impl/= 各写方法（=upsert_resource= / =delete_resource= / =resolve_links= / =transition_task= / =add_attachment= / =create_community= / =derive_artifact= / =export_skill= / =sync_push= / =sync_pull=）入口加三件套调用。
   - =core/tests/write_check.rs= 3 个单元测试。
   - =cli/src/main.rs= =exit_code_for= 加 =AddressUniqueness -> 10=。
   - 验证 =cargo test --workspace= 0 回归。
   - 1 commit。
3. *阶段 3 — 切调用面*：
   - =cli/src/main.rs= / =cli/src/mcp/server.rs= =use= 行加 9 个 use-case trait 引入。
   - 所有 =service.<fn>()= use-case 调用 → =<AppFacade<_> as TraitUseCase>::fn(&mut service, ...)=。
   - =cli/src/main.rs= 加 =--capability-filter= flag；=service.register_capability= 之后调用 helper 应用过滤。
   - =mcp/server.rs= =inspect= tool 拆为 =inspect_rules= + 保留 =space_doctor=。
   - 旧孤儿 =crates/cli/tests/mcp/inspect_*=（如有）迁移到 =crates/cli/tests/inspect_rules_mcp.rs=。
   - =crates/cli/tests/cli_write_checks.rs= 端到端验证。
   - 验证 =cargo test --workspace= 0 回归。

每阶段完成后立即跑 =cargo test --workspace= 验证 0 回归，再继续下一步。阶段 1 + 2 + 3 可在同一天完成，但分三个 commit 便于回滚。

* 6. 风险与缓解

- 风险：=service.rs= 1740 → ≤400 行的 god-impl 拆分时，可能出现方法体的 =self= 借用冲突（多个 trait 方法签名类似但参数不同）。缓解：每个 =use_cases_impl/<trait>.rs= 是独立 =impl= 块，Rust 允许多个 trait 在同一类型上各自 impl；按 trait 顺序逐个迁移，每步跑 =cargo test --workspace= 验证 0 回归。
- 风险：CLI =main.rs= 1391 行同步改 =service.fn → Trait::fn(&mut service)= 量大。缓解：先做阶段 1（拆 mod，不动调用面），阶段 3 再统一改调用面；调用面改动按 9 个 trait 分 9 个 sed-replace 子批次，每批跑 =cargo test --workspace= 验证。
- 风险：写操作三件套的 capability 检查在所有写路径上加，可能误伤既有测试（如 =api_source.rs= 的 =add_attachment= 测试）。缓解：=check_capability= 只检查 catalog 是否含该 capability id，9 个 built-in capability 全注册（=with_builtins= 行为不变），所以既有测试不会触发 =UnsupportedCapability=；只有 =--capability-filter= 显式剔除时才会失败。
- 风险：MCP =inspect= tool 改名 =inspect_rules= 破坏既有客户端。缓解：0.5 spec 已要求「MCP inspect 使用真正的 inspect 用例」，本 spec 落地是 spec 推进；MCP 客户端由同仓库控制（无外部客户），旧 =inspect= tool 一次破坏性删除可接受。
- 风险：=check_address_uniqueness= 实现需要 catalog 中维护「address → ref」映射，=ResourceAddress::from(ResourceRef)= 不一定唯一（多个 locator 解析到同一 ref）。缓解：本轮只对 =ResourceAddress::Ref=（直接 =ref= 输入）做检查；=LinkTarget= / =Locator= 路径暂时跳过（0.6 journal 落地后再做）。
- 风险：=check_revision= 在写操作中要求调用方传 expected revision，但 CLI =upsert_resource= / =task transition= 当前不传 expected（CLI 命令形如 =notez task transition <ref> --to DONE=）。缓解：CLI 默认 =expected=""=，=write_check::check_revision= 把 =expected=""= 当作「无条件覆盖」（0.6 journal 引入后才会强制 expected）；本 spec 落地时 =cli/src/main.rs= 写命令不传 expected，=check_revision= 直接放行。
- 风险：本轮新增 =ApplicationError::AddressUniqueness= 变体，导致手写 =serde= impl 增多。缓解：参照现有 =RevisionConflict= 分支风格，加 ~20 行 =match= 分支；手写 impl 与派生 =Serialize/Deserialize= 不冲突。
