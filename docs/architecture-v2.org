本文档是对现有实现的全面评审结论与目标架构设计。诊断部分全部基于代码证据（含三份并行审计），不是对 [[file:architecture.org][Notez 架构]] 的复述。目标架构以 SICP 的核心方法论（基本元素 / 组合手段 / 抽象手段 / 流 / 元语言抽象）组织，并对齐主流工程模式（端口与适配器、CQRS、事件溯源、单向数据流）。

* 1. 本质问题

系统要同时保住四件事：文件主权、异构来源接入、同一对象跨空间组合、人类客户端与 Agent 同规则读写。当前实现把这四件事都声明为目标，但在三个层面系统性偏离：

1. *底层*：领域内核（domain）是干净的，但应用层把「编排骨架 + 具体基础设施 + 错误分类 + 能力元数据」揉在一个泛型门面里；没有事件脊柱，同步的三路合并在结构上不可能工作。
2. *协议*：同一个用例存在四套互相独立的请求模型（CLI / MCP / 应用层位置参数 / preview 私有 DSL），且已经实际发散。三个表面跑在两个不同的运行时装配上。
3. *交互与 UI*：Web 是纯 SSR 静态 HTML 加内联脚本补丁，大量按「有水合客户端」写的处理器永远不执行；桌面 / 移动端是不相干的脚手架；没有设计系统。

根因只有一个：*领域内核没有从基础设施中真正剥离*，导致客户端无法拥有可运行的运行时（wasm32 编不出有用的客户端），于是所有交互退化成表单提交和页面跳转；而服务端为了补交互又绕过了自己的组合根。

* 3. SICP 设计透镜 → Notez 映射

SICP 给出的不是一套模式，而是评价语言/系统的三条标尺：*基本元素是什么，如何组合，如何抽象*。以此重审 Notez：

| SICP 概念 | Notez v2 对应物 | 现状差距 |
|-----------+-----------------+----------|
| 基本元素 (primitives) | =ObjectId= / =ResourceRef= / =Locator+TextSpan= / =Change= / =Relation= / =Capability= / =Principal+Scope= | 身份与关系已存在；Change 与 Principal 缺位（B5） |
| 组合手段 (combination) | Space = 引用集 × 语义（排序/标签/视图/授权）；SavedQuery = 谓词组合；View = fold(Change 流)；Artifact = recipe(Community) | Space 组合语义未落地（跨空间引用是 MVP-1 未竟项）；View 不是折叠产物而是全量重扫 |
| 抽象手段 (abstraction) | 一个用例 = 一个 Request/Response 类型，统一经 Dispatcher 分派；端口隐藏表示 | 四套请求模型并存（P1/P2）；具体存储泄漏（B2） |
| 数据抽象 (data abstraction) | constructor/selectors 契约：=ResourceRef::parse/to_string=；表示隐藏在端口后 | UI DTO 反向伪造身份（H4）；宽口 trait 混杂读写（B3） |
| 消息传递 / 泛型操作 (data-directed) | SourceRegistry 按 =(SourceKind, 操作)= 分派；CapabilityCatalog 即操作表 | 已有雏形，但要升级为统一 Dispatcher 的注册表机制 |
| 流 (streams) | Change journal = 事件流；投影 = 流的折叠；同步 = 流合并（真实因果父）；UI signal = 流的当前值投影 | 流完全缺位：无 journal（B5）、假祖先（B6）、UI 无失效刷新（U1） |
| 元语言抽象 (metalinguistic) | Selector 查询代数 + 解释器；=notez://object|query|code= URI 文法；PARA/看板 = 命名查询 | Selector 是固定结构体非代数；看板/查询驱动视图未实现 |

关键判据：*每个新需求应该表现为「新增一种组合或一个新的注册表条目」，而不是修改既有抽象的签名*。当前新增一个查询过滤维度要同时动 Selector、trait、SQLite、CLI、MCP 五处 —— 这就是抽象手段缺失的直接度量。

** 4.3 统一协议与 Dispatcher（抽象手段）

- 每个用例一对类型：如 =QueryRequest{ selector: SelectorExpr, page }= → =QueryResponse{ rows, total }=。全部住 =notez-protocol=，派生 =Serialize/Deserialize/JsonSchema=。
- =Dispatcher= 把 =RequestKind → Handler= 存入注册表（SICP 的 put/get 表）。CLI/MCP/HTTP/Web 都把各自输入翻译成同一种 Request：
  - CLI：clap 枚举 match 后构造 DTO —— 字段齐全性由编译器强制，P2 类发散不再可能；
  - MCP：工具输入 schema 由 =schemars::schema_for!(QueryRequest)= 生成，删除 14 份手写；
  - HTTP：axum extractor 直接反序列化 DTO；
  - Web：水合客户端经 HTTP/server function 发送同一 DTO。
- 横切关注点单点化：授权（Principal × Space × Source × Action × Scope）、revision 写检查、审计记录、trace 全部挂在 Dispatcher 一处。这是 MVP-2 验收场景 3/5 的结构性保证。
- 现有 =CapabilityCatalog= 九个描述符升级为该注册表的元数据源（同时修正 B8 的 Mutability 谎报）。

** 4.4 事件脊柱（流）

- =Change { id: Ulid, hlc, actor: Principal, source_id, op, targets: [ResourceRef], expected_revision, payload_ref }=。
- =EventJournal= 端口：=append= / =since(cursor)= / =by_target=。native 实现 = SQLite 表 + =.notez/journal.ndjson= 镜像（日志本身是历史，不属可重建投影；NDJSON 形态保住文件主权，可 diff 可备份）。
- 一切写路径收敛为：Command → 领域校验 → 生成 Change → journal 追加 → Projector 折叠进投影 → 各表面收到失效通知。
- 同步修复（B6）：push 时写入真实 =parent_snapshots=（heads 按 actor 维护真实因果史）；pull 在对象库中找共同祖先内容再做三方合并；无法合并 → =ConflictRecord=（已有域类型）+ 显式冲突状态。relay/P2P transport 保持端口，接不接由 roadmap 决定，但引擎只面向 Change 流。
- 收益即时兑现：审计 = journal 投影；离线队列 = 未投递 Change；冲突可见性 = ConflictRecord 查询 —— 规范 §7 全部条款有了单一机制载体。

** 4.5 读模型与查询解释器（元语言抽象）

- =SelectorExpr= 代数：=And/Or/Not/KindIn/TitleContains/Tag/HasRelation{kind,direction}/InSpace/Fulltext= ，纯数据、可序列化。
- 解释器 =eval(expr, &ProjectionReader)=；SQLite 实现负责下推，内存实现用于测试与 wasm。
- SavedQuery = =notez.toml= 里的命名 =SelectorExpr=；PARA 分类 = 关系 + 命名查询；看板 = 命名查询的列投影。拖卡片 =task transition= Command（走 Dispatcher 授权/审计路径），符合规范 §6/§10 场景 7。
- =notez://query/<id>= 直接引用命名查询，URI 文法与解释器同源。

** 4.6 保真写回（数据抽象闭环）

- 解析时保留 =TextSpan=（已有）。=SourceWriter= 端口：=apply(locator, Vec<TextPatch>)=，patch 以 span 定位做外科替换，禁止整文覆盖。
- org/markdown 各实现一个 writer；=mutate= 整体载荷语义删除。这是 MVP-1「写回不得倒灌正文」门槛的落地件。

** 4.7 交互与 UI 重设计

运行时形态：

#+begin_src text
浏览器 ── SSR 首屏(壳+数据) ──► 水合 WASM 客户端
                                    │  Action
                                    ▼
                              Client Store (signals)
                                    │  Dispatch(Request)
                                    ▼
                              HTTP API / server fn
                                    │
                          Engine Dispatcher（服务端）
                                    │ Response
              Client Store 更新 ──► View 重渲染（单向数据流）
#+end_src

- *单向数据流*：Action → Dispatch → Response → Store（spaces / 当前 source / 资源缓存 / 同步与审计状态）→ View。Dioxus signal 只作机制，不做跨组件隐式全局；扫描/watch 完成后由 Store 失效刷新取代「重定向拿新页」。
- *水合的前提*正是 4.2 的拆分：客户端只依赖 =notez-domain + notez-protocol + ui=，永不见 rusqlite/tempfile。engine 若需嵌入客户端（本地直连模式）也具备编译资格，但首版走 HTTP。
- *交互债务清零*：删除内联面板 JS shim；palette Enter 导航、列表过滤实时性、watch 启停（修 H2 参数错）全部经由 Action 路径实现并验收；删除一切不水合的死处理器。
- *安全*：预览 HTML 由 builder 输出改为「结构化渲染树 → 前端 RSX 渲染」或至少集中一个净化出口；=dangerous_inner_html= 收敛到单点并加转义测试（U3）。
- *设计系统*（主流做法，token 优先）：
  - =packages/ui/tokens.css=：色彩/字阶/间距/圆角/阴影 CSS 变量，暗色主题为变量切换；

* 6. 风险与非目标

风险：

1. *更名涟漪*（M1）：workspace 级机械改动，量大但低智；一次提交完成，避免长期双名。
2. *事件脊柱触碰所有写路径*（M3）：沿用 0.5.x-A2 的「逐 trait 迁移、每步全量测试」节奏；过渡期允许旧直写路径与新 journal 并存，但新路径必须先覆盖全部写用例才删旧路径。
3. *Dioxus 水合已知痛点*（M6）：git 史显示 fullstack 装配曾踩 =Router<()> 闭包坑与 wasm rustflags；对策：自定义 axum 路由合并优先策略保留，水合按页灰度，每页过浏览器实测。
4. *范围诱惑*：CRDT、多人实时协作、Notion/Anytype 双向仍是非目标（继承规范 §9）；Change 流为其预留接口但不实现。

非目标（本轮明确不做）：

- 不换技术栈（Dioxus/Rust/SQLite 维持）；
- 不追求任意格式完美无损双向转换；
- 不做自动解决所有远程冲突；
- 不在本设计中实现 Notion/Anytype/网页摘录 Adapter。
